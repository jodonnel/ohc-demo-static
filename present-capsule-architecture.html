Capsule Architecture

What Capsules are, why you need them, and how content flows
Opening context: "This is a practical walkthrough. We want you to understand the architecture so you can make good decisions about where to put Capsules and why."

What Is a Capsule?

  • Regional mirror + proxy that brings Satellite services to your hosts' location
  • Hosts register to the Capsule, not to the Satellite
  • Satellite remains the single authority -- Capsules don't make policy decisions
Satellite is the library catalog. Capsules are the branch libraries. The catalog decides what's on the shelves. The branches serve the local readers.
The branch library analogy works well with non-technical stakeholders. Satellite = central catalog, Capsule = local branch.

The Cost of Centralization

  • WAN bandwidth -- every host pulling RPMs across the wire doesn't scale
  • Single point of failure -- if the Satellite is unreachable, no site can patch
  • Compliance gaps -- hosts that can't reach content drift out of policy silently
If your WAN goes down, can your sites still patch?
Ask the room directly. "Has anyone here had the WAN go down and realized their remote sites couldn't get security updates?" This is the pain point that sells Capsules.

Segregated Networks

  • Satellite stays behind the firewall -- never exposed to untrusted zones
  • Capsule sits where the hosts are -- firewall rules stay clean
This is the slide that matters most for a regulated financial org. Satellite itself never needs to be reachable from restricted zones.

Regional Resilience

  • Restore from backup -- minutes to hours, full recovery
  • Re-register a fresh Capsule + sync -- hours, depends on content volume
  • Repoint hosts at another Capsule -- immediate, but incurs architectural debt
Regional backup = regional resilience. Each Capsule is independently recoverable. The cost is one VM. The risk of not having one is a site that goes dark.
If Belgium loses their Capsule, they recover from a local backup -- they don't wait for Virginia to ship content across the Atlantic.

  • Architecture patterns carry forward -- hub-and-spoke, DMZ, regional
Invest in topology now -- it carries into Satellite 7.
Nothing you build today is throwaway. Capsule architecture is topology, and that topology persists into Satellite 7.

Certificate Architecture

  • Satellite runs its own CA -- each Capsule gets a cert signed by it
  • Hosts trust the Satellite CA -- imported during registration
  • Clone gotcha: cloned Capsule has new IP, cert mismatch -- run satellite-change-hostname and reimport CA
The clone gotcha is something that bites people in DR scenarios. If you clone a Capsule for failover, the cert won't match the new hostname/IP.

Content Sync Internals

Sync Modes

  • Immediate -- triggered on publish or promote
  • Scheduled -- cron-based, you set the window
  • Concurrency -- pulpcore_worker count controls parallel tasks

Bandwidth + Storage

  • Sync over HTTPS (port 443)
  • download_policy: on_demand -- lazy sync, RPMs fetched when hosts request them
  • On-demand can cut storage by 60-80%
On-demand download policy can cut Capsule storage by 60-80%. Only downloads an RPM when a host actually requests it.
On-demand is the big win for orgs with large content libraries but limited Capsule disk. The RPM is fetched once, then cached locally.

Hub and Spoke at Scale

  • Content Views count affects sync time -- more CVs = longer sync per Capsule
  • Stagger sync windows to avoid saturating WAN bandwidth
For orgs with 6+ Capsules, sync scheduling becomes a real operational concern. Stagger windows by region/timezone.

DMZ Deployment -- Network Flow

Emphasize: Satellite initiates the sync outbound. The DMZ Capsule never reaches back into the trusted zone unsolicited. This is the critical security posture for financial services.

Capsule HA Patterns

Load-Balanced (Active/Active)

  • HAProxy or F5 in front of multiple Capsules
  • Content availability + registration redundancy
  • Each Capsule syncs independently -- no shared state

Active/Passive

  • Shared storage between primary and standby
  • Failover is manual or scripted
  • Simpler, but recovery depends on storage layer
Most orgs don't need Capsule HA. One Capsule per site with good backups is usually enough.
Don't oversell HA. The realistic answer for most sites is a single Capsule with tested backups. HA adds complexity without proportional benefit unless you're at massive scale.

Capsule Backups -- Operational

  • satellite-maintain backup -- same tooling as Satellite server backups
  • Full vs incremental -- daily incremental, weekly full is the standard cadence
  • Storage: local backup + remote copy (NFS, S3, tape -- whatever your org uses)
Recovery procedure: restore to same hostname/IP, reimport certificates, verify sync status. Test restores quarterly.

An untested backup is not a backup.
Ask the room: "When was the last time you actually tested restoring a Capsule from backup?" If the answer is "never," that's the action item.

Image Mode + Capsule

  • bootc / OSTree content flows through Satellite like any other content type
  • Satellite manages ostree repos and container images -- Capsule mirrors them
  • Same Content View / Lifecycle Environment model applies to image content
Image Mode doesn't change Capsule architecture -- it adds a content type. Hosts pull bootc updates from their local Capsule the same way they pull RPMs.
This is forward-looking. Image Mode is the future of RHEL deployment, and the architecture you build today already supports it.

Content View Composition

Composite Content Views

  • Combine RHEL BaseOS + AppStream + custom repos
  • Add Puppet / Ansible content into one promotable unit
  • Single version number tracks the entire stack

Filters

  • Include / exclude by package name or pattern
  • Errata filters by date, type, or severity
  • Date-based filters for predictable patching windows
Use date-based errata filters for predictable patching windows. "Everything published before April 1" gives you a stable, repeatable baseline.
Composite CVs are where the Content View model really pays off for large orgs. Instead of managing 12 individual CVs, you compose them into a single promotable unit.

Satellite 7 -- What Changes for Capsule Ops

  • new Containerized deployment -- podman-based, Capsule becomes an image pull + configure
  • Migration path from 6.x -- documented upgrade, not a rip-and-replace
  • Foreman / Katello still underneath -- same engine, new packaging
Architecture topology is unchanged. Hub-and-spoke, DMZ, regional patterns all carry forward. What changes is how you deploy and update -- not what you deploy.
The key message: Satellite 7 changes the deployment model, not the architecture model. Everything they build today is investment, not throwaway.

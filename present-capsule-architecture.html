Red Hat Satellite
Capsule Architecture

What Capsules are, why you need them, and how content flows
Opening context: "This is a practical walkthrough — not a deep-dive admin session. We want you to understand the architecture so you can make good decisions about where to put Capsules and why."

The Problem

  • One Satellite server manages content, subscriptions, and policies centrally
  • Multiple locations — different sites, different networks, different countries
  • Bandwidth is expensive — every host pulling RPMs across the WAN doesn't scale
If you have hosts in more than one location, or hosts in networks that can't reach your Satellite directly — you need Capsules.
Keep this conversational. "Has anyone here had the experience of 500 hosts all trying to pull a RHEL update across the WAN at the same time?"

What Is a Capsule?

  • Regional mirror + proxy — brings Satellite services to your hosts' location
  • Hosts register to the Capsule, not to the Satellite
  • Satellite stays the single authority — Capsules don't make policy decisions
Think of it this way: Satellite is the library catalog. Capsules are the branch libraries. The catalog decides what's on the shelves. The branches serve the local readers.
The branch library analogy works well with non-technical stakeholders. Satellite = central catalog, Capsule = local branch.

Hub and Spoke

Draw their attention to the fact that the EU Capsule is the same architecture — geography doesn't change the pattern. Each Capsule syncs from Satellite on a schedule you control.

What Flows Through a Capsule

Content

  • RPM repositories (RHEL, custom)
  • Errata (security, bugfix, enhancement)
  • Kickstart trees for provisioning
  • Container images (if configured)

Services

  • DHCP, DNS, TFTP (bare-metal provisioning)
  • Ansible / Puppet configuration
  • OpenSCAP compliance scanning
  • Host registration + subscription
A Capsule can run all of these services or just content mirroring — you decide per site.
This is where you gauge the room. If they only care about content mirroring, don't spend time on DHCP/TFTP. If they're doing bare-metal provisioning, that's a different conversation.

  • Content View = curated subset of all available repos and errata
  • Lifecycle Environments = promotion path (Dev → Test → Prod)
  • Capsules sync only what's promoted to the environment they serve
This is how you do controlled rollouts. A patch doesn't reach production hosts until it's been promoted through every gate — and the Capsule only gets what its environment allows.
This is the money slide for governance people. The pipeline means no patch reaches production without deliberate promotion. For a regulated org, this IS the compliance story.

Capsules in Segregated Networks

  • Satellite never directly exposed to untrusted networks
  • Capsule sits where the hosts are — firewall rules stay clean
  • Common in financial services, healthcare, defense
This is the slide that matters most for a regulated financial org. Their security team will care that Satellite itself never needs to be reachable from restricted zones. The Capsule is the only thing exposed.

Capsule Sizing — Rules of Thumb

  • One Capsule per ~3,000 hosts (content-only; fewer if running provisioning services)
  • Storage scales with Content Views — more repos synced = more disk
  • Minimum: 4 cores, 20 GB RAM, 300+ GB disk (content dependent)
  • Sync schedule matters — stagger Capsule syncs to avoid saturating WAN links
Don't over-consolidate. One Capsule per site is the default assumption. If a site has 200 hosts or 2,000 — it still gets a Capsule. The cost is one VM. The risk of not having one is a site that goes dark during a WAN outage.
The "one Capsule per site" framing cuts through overthinking. It's a VM. It's cheap insurance. The alternative is hosts that can't get patches when the WAN flaps.

Capsule Backups — Regional Resilience

  • Each Capsule should be independently recoverable
  • satellite-maintain backup works on Capsules — same tooling as Satellite
  • If a Capsule dies: hosts keep running on cached content, but can't get new updates or register new hosts
Recovery options — fastest to slowest:

1. Restore from backup → minutes to hours
2. Re-register a fresh Capsule + sync → hours (depends on content volume)
3. Point hosts at another Capsule or Satellite directly → immediate but architectural debt
This was the specific topic their contact asked about. Regional backup = regional resilience. If Belgium loses their Capsule, they recover from a local backup — they don't wait for Virginia to ship them content across the Atlantic.

How to Open
Spring-loaded posture

"The question you're really asking is: how do we patch kernel CVEs without scheduling a SAP maintenance window every time? Here's the three-layer answer."

The goal isn't to respond faster to a CVE — it's to already be positioned before the alert fires. Satellite has the content synced. AAP has the playbook tested. kpatch applies in-memory in minutes.

Detect → Deliver → Execute → Verify:

  • Detect: Red Hat Insights — CVEs mapped to your nodes
  • Deliver: Red Hat Satellite — content management, kpatch-patch RPMs
  • Execute: Red Hat Ansible Automation Platform — orchestrates, audit trail
  • Verify: kpatch list + Insights CVE status closed
kpatch
Live kernel patching — the immediate win
23 days → under 4 hours for kernel CVE cycle (Forrester TEI)
  • Patches kernel CVEs in-memory — HANA stays running
  • Certified with SAP HANA since 2018 (SAP Note 2382421)
  • No reboot required for ~95% of critical kernel CVEs
  • No SAP maintenance window

kpatch defers the reboot, it doesn't eliminate it. They still reboot eventually for glibc, OpenSSL, userspace. kpatch lets them take the reboot on their schedule — not at 2am during an active CVE.

E4S + Image Mode
Layers 2 and 3

Extended Update Support (E4S): Stay on a SAP-certified minor release forever. Red Hat backports security patches — no minor version bump required. Bundled in RHEL for SAP Solutions sub.

Current sweet spot: RHEL 9.6 — E4S until Nov 2028, latest features, SAP-certified.

Image Mode (horizon): bootc-based, immutable OS. Patch = image pull + rollback. RHEL 10 GA Feb 2026, SAP HANA certified. Honest caveat: 2TB-RAM HANA rebuilds are expensive. Don't push this on existing nodes.

"E4S decouples kernel CVE patching from SAP version upgrades. kpatch handles what can't wait. Satellite delivers both. That's the whole strategy."
